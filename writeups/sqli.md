# SQL Injection — обзор и эксплуатация (OWASP / PortSwigger)

## Summary
SQLi позволяет атакующему изменять целиком или частично команды к БД при помощи конкатенации, что приводит к утечке credentials и secrets. Данная уязвимость является следствием raw запросов вместо параметризованных.

## CWE
CWE-89 — Improper Neutralization of Special Elements used in an SQL Command (Неправильная нейтрализация специальных элементов, используемых в SQL-команде)
CWE-89 — точный CWE для SQL-инъекции

## Severity
Critical. SQLi открывает прямой доступ к БД (creds, PII, карты), возможность выгрузки всей базы, обхода auth.

## Root cause
Из-за конкатенации - доверие вводу пользователя, данным, подконтрольным атакующим. Запрос к БД воспринимает данные пользователя, как часть запроса. 

## Виды (как получаешь результат)
### In-band
- WHERE / login bypass: при помощи инъекций в строку в логином (' OR 1=1 -- или administrator'--) атакующий отрезает проверку пароля в запросе к БД, тем самым пропускает этап авторизации и происходит вход в систему под логином администратора (в первом случае происходит вход под данными пользователя, находящегося первым в БД)
- UNION-based: в поле с запросом к БД приписываешь UNION SELECT NULL,NULL ("NULL" должно быть ровно столько, к скольким объектам обращается запрос в БД, а также их типы должны совпадать). Типы необходимо проверить путем подставления 'a' вместо NULL по порядку перебором. 
### Blind (результат не виден)
- Boolean: сначала проверяем уязвимость путем добавления к запросу <' AND 1=1--> - если длина ответа равна длине ответа без добавления инъекции, то идем дальше. Вторым шагом находим длину пароля: ' AND (SELECT username FROM users WHERE username='administrator' AND LENGTH(password)>N)='administrator. (N - длина пароля-1 после ложного срабатывания). Далее перебор пароля путем добавления следующей команды - <' AND SUBSTRING((SELECT password FROM users WHERE username='administrator'),1,1)='a>
- Time-based: В этом случае уже длина ответа одинаковая и проверяем возможность инъекции путем добавления команды "отложенного ответа" при помощи pg_sleep(5) или SLEEP(5) или WAITFOR DELAY '0:0:5'. Вот пример: '||pg_sleep(5). Далее применяем инъекцию: '||(SELECT CASE WHEN (SUBSTRING(password,1,1)='a') THEN pg_sleep(5) ELSE pg_sleep(0) END FROM users WHERE username='administrator')--. И далее автоматизация при помощи Burp Intruder (Cluster Bomb)

## Steps to Reproduce (PoC — из лаб)
UNION-кража кредов:
1. Определяем количество столбцов UNION SELECT NULL,NULL..→ сколько NULL получилось ввести без ошибки - столько и столбцов
2. Найти текстовые столбцы при помощи подстановки и перебора NULL на 'a'
3. UNION SELECT username,password,NULL FROM users -- → вытащить creds
4. вход под administrator
Boolean blind:
1. Проверяем наличие уязвимости - ' AND 1=1 --
2. Выясняем длину пароля ' AND (SELECT username FROM users WHERE username='administrator' AND LENGTH(password)>N)='administrator
3. Подбираем пароль при помощи Burp Intruder
4. Вход под administrator

## Impact
Что даёт SQLi: обход аутентификации, доступ и выгрузка всей БД. хеши паролей → offline-брут, PII/карты → юр. последствия, в тяжёлых случаях изменение/удаление данных или RCE (Remote Code Execution).

## Fix
1. ОСНОВА — параметризованные запросы. Сначала БД принимает структуру запроса и только после этого уже исключительно как данные вставляет на место плейсхолдеров "?" ввод пользователя без возможности влияния на запрос.
2. НЮАНС — структурные части (ORDER BY, имена столбцов) не параметризуются → необходимо создать allowlist имен столбцов, к которым разрешено обращение.
3. Рекомендуется использовать ORM, так как они по умолчанию используют параметризованные запросы. Однако там есть какие-то ограничения, которые пользователи обходят, добавляя свои raw-склейки, тем самым убивая смысл ORM → SQLi активируется.
4. least privilege БД-аккаунта. Необходимо выдать БД только те таблицы и права действий, ТОЛЬКО которые НЕОБХОДИМЫ для работы.
5. доп.слои — валидация форматных полей, скрытие ошибок, WAF (это не панацея, только отсечение ожидаемых атак)

## Detection (как поймать в пайплайне)
SSDLC:
- DAST/ручной: Burp, sqlmap или проверка ' в каждой строке запроса к БД
- SAST: data-flow: (source) ввод пользователя -> конкатенация -> cursor.execute() (sink) (после обнаружения подбного пути без параметризации данный путь помечается как SQLi). где пропускает: ORM-обёртки, хранимые процедуры 
- SDLC: Рождается на Coding (конкатенация вместо параметризации), предпосылка — на Design. Ловится когда строится логика и структуразапросов к БД. Детектится на code review (.raw(), .execute()) и Testing.
