# Атака 1: JWT alg:none — обход проверки подписи (OWASP Juice Shop)

## Summary
Приложение не проверяет подпись, если в header указан alg:"NONE". Благодаря этому подделывается payload и есть возможность сменить пользователя на любого существующего и обойти авторизацию.

## CWE
CWE-347 — Improper Verification of Cryptographic Signature
(+ можно CWE-345 — недостаточная проверка подлинности данных)

## Severity
Оценка: Critical - рушится вся система идентификации пользователей. Приложение не может больше доверять ни одному токену, так как любой из них может быть подделан. Эксплуатируется тривиально готовым инструментом, без спец-условий

## Root cause
Ошибка дизайна: сервер определяет алгоритм по полю alg из самого токена - то есть доверяет данным, которые контролирует атакующий. Проверяющая сторона не должна принимать от проверяемой решение о том, как её проверять. Ошибка реализации (blocklist=="none", пропускающий NONE). payload — открытый Base64

## Steps to Reproduce (PoC)
1. Логин, получить токен (alg: RS256).
2. *python3 jwt_tool.py <token>* / ручная сборка: header {"alg":"NONE"}, payload с role:admin, пустая подпись. Сменил role:"customer" на "admin"
3. Удалить If-None-Match, подставить Authorization: Bearer <токен>.
4. GET /rest/admin/application-configuration → 200 + админский конфиг.

## Impact
Атакующий контролирует весь payload и может выполнить горизонтальную (действовать от имени любого пользователя) и вертикальную (role: customer -> admin) эскалации. Так как подделан может быть любой токен, сервер больше не может доверять ни одному токену. Это полный обход аутентификации и авторизации для всех учеток.

## Fix
Allowlist: сервер принимает ТОЛЬКО RS256, игнорирует alg из токена.
Ссылка на principles.md → allowlist > blocklist.

## Detection (как поймать в пайплайне)
DAST/ручной тест ловит надежно (jwt_tool -X a). SAST должен увидеть: код проверки токена, где алгоритм берется из самого токена. При кастомной логике проверки - может пропустить.
Рождается на Design, дешевле всего предотвращается threat modeling'ом, ловится на этапе Testing

# Атака 2: RS256 → HS256 Key Confusion

### Механика
Сервер выдаёт токены на RS256 (подпись — приватный ключ, проверка — публичный).
Логика проверки берёт алгоритм из поля `alg` токена → тем же доверием, что и alg:none.
Атакующий делает НОВЫЙ токен с alg:HS256 и подписывает его публичным ключом сервера
как HMAC-секретом. Сервер, доверяя alg, уходит в HMAC-ветку → берёт свой проверочный
ключ (публичный RSA) как HMAC-секрет → подпись сходится.

### Почему работает
Публичный ключ RSA открыт by design (JWKS). В HMAC ключ проверки = ключ подписи.
Значит атакующий, зная публичный ключ, может создавать валидные подписи.
Приватный ключ не участвует — RSA-ветка проверки не запускается.

### PoC (Juice Shop)
1. Достать публичный ключ: python3 jwt_tool.py <token> -X s (ссылка на JWKS-эндпоинт Juice Shop в ответе команды)
2. JWK → PEM: <jwks_to_pem.py>
3. подмена data.role на admin (python3 jwt_tool.py <token> -T) + python3 jwt_tool.py <token(из прошлой команды)> -X k -pk public.pem
4. Authorization: Bearer <token> → GET /rest/admin/application-configuration → 200

### Detection
DAST/ручной: Ловится jwt_tool -X k
SAST: при верификации JWT список algorithms должен принимать только то значение, что в коде, но никак не из token.header.alg. Один ключ обслуживает и RSA-, и HMAC-ветки.
SDLC: Рождается на Design, предотвращается treat modeling, ловится на Testing

## Root cause (обе атаки)
Один корень: сервер доверяет полю `alg` из токена — принимает от проверяемой
стороны решение о том, как её проверять. alg:none и confusion — два вектора
одной ошибки. Blocklist (запрет "none") не лечит — он сохраняет доверие к alg.

## Fix (обе атаки)
Allowlist: verify(token, key, algorithms=["RS256"]) — сервер не читает alg как
руководство, а жёстко фиксирует алгоритм в коде. Убирает доверие → закрывает оба вектора.
