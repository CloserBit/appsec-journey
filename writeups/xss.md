# Cross-Site Scripting (XSS) — обзор и эксплуатация (OWASP / PortSwigger)

## Summary
XSS - внедрение JS скрипта в код страницы приложения. Исполнение либо в браузере другого пользователя, либо сохранение скрипта на сервере с дальнейшим исполнением у всех пользователей приложения.

## CWE
CWE-79 — Improper Neutralization of Input During Web Page Generation
Указан специфичный CWE, специально для типа XSS, максимально узкий.

## Severity
High - атака на пользователей приложения (масштаб большой: либо все пользователи, если stored, либо меньшее при reflected/DOM). Critical очень редко.

## Root cause
Доверие данным ввода атакующего. Отсутствие экранирования данных пользователей.

## Виды
### Reflected
После ввода <script>alert(1)</script> в поиск - скрипт попал в URL после знака ?q=. Скрипт выполнился, потому что к данным ввода не было применено экранирование. После перехода пользователя по подобной ссылке можно выполнить действия при помощи скрипта при помощи его session-cookie. 
### Stored
Payload попал в комментарий, который сервер сохранил в БД. Данный комментарий видят все пользователи, перешедшие в описание продукта. Атака: скрипт, внедренный в комментарий срабатывает у всех, кто перешел в описание продукта.
### DOM-based
Запросы, оставленные после # в URL обрабатываются клиентским JS, а не сервером, поэтому данные не обрабатываются и вставляются в JS страницы как есть. Атака - исполнение кода прямо в браузере жертвы.

## Steps to Reproduce (PoC — из лаб)
Reflected: вставляешь данные в интерактивное поле, например, поиска и отправляешь запрос search?q=<script>alert(1)</script> → на страницу приходит уведомление.
Stored: оставляем комментарий <script>alert(1)</script> под продуктом. Он отображается у всех пользователей, перешедших в описание данного продукта → скрипт, оставленный в комментарии исполняется
Обход фильтра (сложная лаба): Если разработчик заблокировал большинство тегов и атрибутов, то мы перебираем сначала теги, потом с TP тегами - самовыполняющиеся события и оборачивая данный payload в html страницу с кодом использования данного события - доставляем жертве. Событие выполняется - скрипт срабатывает (событие срабатывает, потому что выполняется на стороне авторизированного пользователя)

## Impact
XSS позволяет красть cookie (при отключенном HttpOnly), действовать от имени пользователя. Большая область поражения при сохранении скрипта в БД приложения.

## Fix (defense in depth)
1. Экранирование (индивидуальное для каждого языка, т.к. HTML-разметка не работает для JS). HTML экранирование заменяет символы ( ", ', & , < , > ) на сущности. Для JS необходимо уже другое экранирование "\"", сущности в нем не работают.
2. CSP (Content Security Policy) - одобряет использование только разрешенных скриптов (allowlist). script-src 'self'
3. HttpOnly (предотвращает кражу session cookie) - блокировка чтения session cookie для JS. Действия от имени пользователя данный флаг не запрещает, так как браузер сам к каждому запросу автоматически прикладывает session cookie.
4. Валидация и санитизация (доп. слои). Валидация - строгий прием/отмена данных (например, для дат, email, телефон). Санитизация - при разрешенной HTML-разметке отсекает любые разметки, кроме разрешенных.

## Detection
- DAST/ручной: перебор тегов, событий в Burp Intruder
- SAST: data-flow — ввод (source) → вывод в HTML/DOM (sink) без экранирования. Проверка куда передаются данные при их вводе по все поля, где это возможно внутри приложения. Пропускает: DOM-XSS (клиентский JS, серверный SAST его не видит) и кастомные механизмы генерации HTML (самописные, не стандартные Jinja/React — data-flow теряется в незнакомом коде).
- SDLC: зарождается на стадии Coding. Ловится на code review (| safe, innerHTML, склейка HTML) + Testing.
