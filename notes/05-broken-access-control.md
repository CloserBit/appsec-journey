*Broken Access Control (A01)* = сломанная авторизация (не аутентификация). Вошёл честно, но сервер не проверяет границы прав. Подтипы:

1. Объектный (IDOR) — чужой объект (/basket/2). «Твой ли объект?»
2. Функциональный — админская функция от юзера (POST /admin/...). «Твоего ли уровня действие?» = вертикальная эскалация.
3. Через параметр — подмена role/isAdmin в запросе. Сервер доверяет клиенту в вопросе прав.
4. Обход метода/пути — защищён GET, не POST; /admin, не /Admin. Корень всех: нет/неполна/доверяет-клиенту серверная проверка авторизации.
Принцип защиты: deny by default + проверка ТОЛЬКО на сервере при КАЖДОМ доступе. Клиентские проверки (скрытая кнопка, route guard) = UX, не безопасность.

*SSRF (Server-Side Request Forgery - подделка запросов на стороне сервера)* — заставляешь СЕРВЕР сделать запрос за тебя туда, куда тебе самому доступа нет. Сервер внутри периметра → ходит во внутреннюю сеть (192.168/10.x), на localhost, к облачным метаданным (169.254.169.254 — облачные креды!).
Где живёт: любая функция, где сервер идёт по URL от пользователя (превью картинки, аватар по URL, «проверить сайт», webhook, импорт).
Атака: вместо картинки подсунуть http://169.254.169.254/... → сервер вернёт облачные ключи.
Корень: сервер доверяет URL от атакующего, не проверяя, КУДА тот ведёт (тот же класс, что alg/id/redirect_uri).

*SSRF — защита.* Blocklist безнадёжен: один адрес (169.254.169.254) пишется десятками способов — десятичным (2852039166), hex (0xA9FEA9FE), октальным, через DNS-домен, через редирект 302. Все ведут туда же, строковый фильтр слеп.
Правильно: (1) allowlist разрешённых назначений, не blocklist запрещённых; (2) проверять РЕАЛЬНЫЙ IP после DNS-резолва и после КАЖДОГО редиректа, а не строку URL; (3) defense in depth — сетевой запрет доступа к метаданным, запрет редиректов.
Урок: blocklist перечисляет «плохое», а плохое кодируется бесконечно → allowlist («разрешено ровно это») надёжнее by design.

*Blind SSRF* — ответ сервера не возвращается пользователю, но атака работает: (1) сканирование внутренней сети по косвенным признакам (время ответа, коды ошибок → какие адреса/порты живы); (2) подтверждение через out-of-band — подсунуть URL на свой сервер, если пришёл пинг → SSRF есть (Burp Collaborator). «Не вижу ответ» ≠ «не уязвимо».
Detection SSRF: DAST/ручной — подсунуть внутренние адреса/метаданные, Collaborator для blind. SAST — data-flow: ввод юзера (URL) → HTTP-вызов (requests.get) без валидации адреса между ними. SDLC: рождается на Design (дать юзеру URL для серверного запроса), ловится threat modeling + review + Testing.
