Токен выглядит как три блока, разделённых точками:
xxxxx . yyyyy . zzzzz
header . payload . signature

*Часть 1 — Header (заголовок). Метаданные о самом токене. Обычно два поля:*
typ: тип, всегда JWT.
alg: алгоритм подписи — например HS256 или RS256. Запомни это поле, оно главный герой будущих атак.

*Часть 2 — Payload (полезная нагрузка). Сами данные о пользователе, их называют claims (утверждения). Бывают:*
стандартные (registered): sub (кто), iat (когда выдан), exp (когда истекает), iss (кто выдал);
произвольные — то, что положило приложение: email, имя, и — внимание — часто роль (role, isAdmin и т.п.).

*Часть 3 — Signature (подпись). Криптографическая «пломба».*
 Сервер берёт header + payload, прогоняет через алгоритм из поля alg со своим секретным ключом и получает подпись. На каждом входящем токене он пересчитывает подпись заново и сравнивает: совпало — токен не трогали, не совпало — подделка, отказ.

- Header и payload — это не шифрование. Это просто Base64URL-кодирование. Кодирование ≠ шифрование: Base64 разворачивается обратно кем угодно, без всякого ключа, в одну команду. Это значит:

Любой, у кого есть токен, читает его payload. Видит твой email, роль, всё. Отсюда железное правило AppSec: *в payload JWT нельзя класть секреты (пароли, номера карт)* — это всё равно что написать их на открытке.

*JWT: сервер не хранит токен — он пересчитывает подпись своим секретом и сверяет. Cookie: сервер хранит сессию, cookie лишь ссылается на неё.*

Как работает проверка подписи сервером?
«откуда сервер знает третью часть, с которой сравнивает?». Он её не хранит — он её вычисляет заново на каждом запросе. Вот механика по шагам для HS256:

Приходит токен header.payload.signature.
Сервер берёт присланные header и payload (первые две части) и считает: HMAC-SHA256(header + "." + payload, СЕКРЕТ).
Получает какую-то строку — это «правильная подпись для этих данных».
Сравнивает её с третьей частью, которую прислал клиент. Совпало → токен подлинный. Не совпало → отказ.

*SAST vs. DAST*
              |          SAST             |  DAST
Приложениене  |  запущено (читает код)    |  запущено (бьёт запросами)
Точка зрения  |  «белый ящик» — виден код |  «чёрный ящик» — только вход/выход
Аналогия      |  инспектор читает чертежи |  инспектор ходит по дому
Когда в SSDLC |  рано (пишешь код / CI)   |  позже (есть рабочий стенд)
Пример        |          Semgrep          |  ZAP, Nuclei
Слабость      |  много false positive     |  не покажет строку кода


SAST — Static Application Security Testing. «Статический» = приложение не запущено, анализируется исходный код, как чертёж дома. Инструмент читает код и ищет опасные places: конкатенацию SQL, захардкоженные секреты, кладут ли password в токен и т.п.

Аналогия: инспектор изучает чертежи дома и говорит «вот здесь проводка проложена у газовой трубы — опасно», не заходя внутрь.
+: находит проблему рано (прямо в коде, до запуска), показывает точную строку.
−: не видит проблем, которые проявляются только вживую; даёт много false positive (ложных срабатываний).
Инструмент из твоего плана: Semgrep (Фаза 4).

DAST — Dynamic Application Security Testing. «Динамический» = приложение запущено, инструмент бьёт по работающему приложению снаружи запросами, как реальный атакующий, и смотрит на реакцию. Код он не видит — только вход/выход, как чёрный ящик.

Аналогия: инспектор заходит в построенный дом, дёргает двери, включает приборы, пробует поджечь и смотрит, что сработает.
+: находит то, что видно только вживую (конфиг, аутентификацию, реальные ответы сервера); меньше «бумажных» ложных срабатываний.
−: находит поздно (нужен работающий стенд), не показывает строку кода, видит только то, до чего дотянулся снаружи.
Инструменты из плана: OWASP ZAP, Nuclei (Фаза 4).

*Как это работает целиком, по шага*
*Момент выдачи (ты логинишься):*

Сервер проверил твой логин-пароль — ок, ты Вася с id:1, role:user.
Сервер собирает payload: {"id":1,"role":"user"}, кодирует header и payload в Base64.
Сервер берёт свой секрет и считает:
signature = HMAC-SHA256(header + "." + payload, super_secret_key_123)
Склеивает header.payload.signature → отдаёт тебе токен.х

*Момент проверки (ты делаешь следующий запрос с этим токеном):*

Приходит токен. Сервер разбивает его на три части.
Сервер выбрасывает присланную третью часть на секунду в сторону и сам заново считает подпись из присланных header+payload своим же секретом:
моя_подпись = HMAC-SHA256(header + "." + payload, super_secret_key_123)
Сравнивает моя_подпись с той третьей частью, что прислал клиент.

совпало → данные не трогали, токен подлинный, пускаем;
не совпало → кто-то менял payload или подделывал → отказ 401.

## Атаки на JWT

### alg:none — обход проверки подписи
- **Суть:** ставим в header `alg: none`, стираем подпись, правим payload.
  Наивный сервер доверяет полю `alg` из токена и не проверяет подпись → пропускает.
- **Root cause:** сервер доверяет `alg` из недоверенного токена. CWE-347.
- **Практика (Juice Shop):** сработал вариант `NONE` → сервер вернул 200.
  Значит в коде blocklist только на нижний регистр (`== "none"`).
- **Fix:** allowlist — жёстко задать на сервере «принимаю только RS256»,
  игнорировать `alg` из токена. (см. principles.md → allowlist)
- **Обнаружение:** DAST/ручной тест (jwt_tool `-X a`). SAST — если видит проверку токена в коде.

HS256 — симметричный (один секрет, HMAC).
RS256 — асимметричный (приватный подписывает, публичный проверяет).
Confusion = заставить сервер проверять RS256-токен как HS256, подсунув публичный ключ в роли HMAC-секрета.

Публичный ключ обязателен: уязвимый сервер считает HMAC-проверку своим ключом (публичным RSA). Подпись атакующего пройдёт шаг 4, только если посчитана тем же ключом. Рандом → HMAC не сойдётся → 401 на шаге 4 (подпись), не на шаге 3 (алгоритм — его уязвимый сервер пропускает).

Confusion не подменяет исходный RSA-токен — атакующий делает НОВЫЙ токен с alg:HS256 и своей HMAC-подписью. Сервер, доверяя alg, уходит в HMAC-ветку кода (if alg=="HS256") и проверяет токен как HMAC — RSA-ветка (и приватный ключ) не запускается вообще. Приватный ключ не «игнорируется намеренно», до него просто не доходит управление.
