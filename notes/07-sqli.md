*SQLi корень:* сервер СКЛЕИВАЕТ пользовательский ввод с текстом SQL-команды в одну строку → БД не отличает команду разработчика от данных юзера → ввод вроде ' OR 1=1 -- вырывается из данных в команду.
' — закрывает кавычку разработчика (вырыв в команду). OR 1=1 — всегда истинно. -- — комментарий, глушит остаток (проверку пароля).
*Опасность:* прямой доступ к БД — credentials, хеши, карты, PII. Обход auth, выгрузка всей базы.
*ФИКС* — НЕ чистка символов (blocklist, дырявo + ломает O'Brien), а РАЗДЕЛЕНИЕ команды и данных: параметризованные запросы. Данные идут отдельным каналом, БД трактует их СТРОГО как значение, вырваться в команду не могут. Корень — смешение; фикс — не смешивать (структурная защита, как allowlist).

Почему параметризация работает: БД парсит структуру запроса (с плейсхолдерами ?) ДО получения данных → структура застывает → данные приходят потом, вставляются как чистое значение, изменить структуру не могут. Склейка наоборот: БД получает готовую строку целиком, ввод меняет структуру.
execute("... WHERE username = ?", (input,)) — ? плейсхолдер, данные отдельным аргументом.
PII — Personally Identifiable Information (имя, email, карта, паспорт). Утечка PII = юр. последствия (GDPR/152-ФЗ), не только техущерб.

*Виды SQLi по получению результата:*
*In-band* (результат в ответе): error-based (данные в тексте ошибки), UNION-based (оператор UNION приклеивает свой запрос → выгрузка других таблиц в вывод).
*Blind* (результат не виден, как blind SSRF): boolean-based (страница по-разному отвечает на истину/ложь → посимвольно угадываешь), time-based (условие → задержка sleep → достаёшь данные по времени ответа).
*«Не виден результат» ≠ «не уязвимо».*

*Time-based blind:* SUBSTRING(password,1,1)='a' → WAITFOR DELAY 5s. Задержка = условие истинно. Посимвольно перебираешь весь пароль. Медленно → автоматизируют (sqlmap, Фаза 4).
Ускорение — бинарный поиск (символ > 'm'?).

*Login bypass SQLi:*
— administrator'-- → войти КОНКРЕТНО админом (указываешь юзера, -- режет проверку пароля). Контролируемо.
— ' OR 1=1 -- → вернуть ВСЕХ юзеров, приложение берёт первого. Кем войдёшь — лотерея (обычно админ первый в таблице, но не гарантия). Работает, но ненадёжно.
Вывод: OR 1=1 = «все строки», а не «нужная строка».

*UNION-based SQLi* — приклеить свой SELECT к оригинальному через UNION → вытащить данные из ДРУГИХ таблиц в вывод страницы. ' UNION SELECT username, password FROM users --
Два правила UNION: (1) одинаковое ЧИСЛО столбцов с оригиналом; (2) совместимые ТИПЫ (текст под текст).
Шаг 1 — узнать число столбцов:
ORDER BY 1--, 2--, 3... → на каком N ошибка, столбцов = N-1.
ИЛИ UNION SELECT NULL--, NULL,NULL--... → при совпадении числа NULL ошибка исчезает.
Шаг 2 — найти текстовые столбцы (заменить NULL на 'a' по очереди — где не ошибка, туда льёшь данные).
Шаг 3 — вытащить данные: UNION SELECT username, password FROM users в нужные столбцы.
