*SQLi корень:* сервер СКЛЕИВАЕТ пользовательский ввод с текстом SQL-команды в одну строку → БД не отличает команду разработчика от данных юзера → ввод вроде ' OR 1=1 -- вырывается из данных в команду.
' — закрывает кавычку разработчика (вырыв в команду). OR 1=1 — всегда истинно. -- — комментарий, глушит остаток (проверку пароля).
*Опасность:* прямой доступ к БД — credentials, хеши, карты, PII. Обход auth, выгрузка всей базы.
*ФИКС* — НЕ чистка символов (blocklist, дырявo + ломает O'Brien), а РАЗДЕЛЕНИЕ команды и данных: параметризованные запросы. Данные идут отдельным каналом, БД трактует их СТРОГО как значение, вырваться в команду не могут. Корень — смешение; фикс — не смешивать (структурная защита, как allowlist).

Почему параметризация работает: БД парсит структуру запроса (с плейсхолдерами ?) ДО получения данных → структура застывает → данные приходят потом, вставляются как чистое значение, изменить структуру не могут. Склейка наоборот: БД получает готовую строку целиком, ввод меняет структуру.
execute("... WHERE username = ?", (input,)) — ? плейсхолдер, данные отдельным аргументом.
PII — Personally Identifiable Information (имя, email, карта, паспорт). Утечка PII = юр. последствия (GDPR/152-ФЗ), не только техущерб.

*Виды SQLi по получению результата:*
*In-band* (результат в ответе): error-based (данные в тексте ошибки), UNION-based (оператор UNION приклеивает свой запрос → выгрузка других таблиц в вывод).
*Blind* (результат не виден, как blind SSRF): boolean-based (страница по-разному отвечает на истину/ложь → посимвольно угадываешь), time-based (условие → задержка sleep → достаёшь данные по времени ответа).
*«Не виден результат» ≠ «не уязвимо».*

*Time-based blind:* SUBSTRING(password,1,1)='a' → WAITFOR DELAY 5s. Задержка = условие истинно. Посимвольно перебираешь весь пароль. Медленно → автоматизируют (sqlmap, Фаза 4).
Ускорение — бинарный поиск (символ > 'm'?).

*Login bypass SQLi:*
— administrator'-- → войти КОНКРЕТНО админом (указываешь юзера, -- режет проверку пароля). Контролируемо.
— ' OR 1=1 -- → вернуть ВСЕХ юзеров, приложение берёт первого. Кем войдёшь — лотерея (обычно админ первый в таблице, но не гарантия). Работает, но ненадёжно.
Вывод: OR 1=1 = «все строки», а не «нужная строка».

*UNION-based SQLi* — приклеить свой SELECT к оригинальному через UNION → вытащить данные из ДРУГИХ таблиц в вывод страницы. ' UNION SELECT username, password FROM users --
Два правила UNION: (1) одинаковое ЧИСЛО столбцов с оригиналом; (2) совместимые ТИПЫ (текст под текст).
Шаг 1 — узнать число столбцов:
ORDER BY 1--, 2--, 3... → на каком N ошибка, столбцов = N-1.
ИЛИ UNION SELECT NULL--, NULL,NULL--... → при совпадении числа NULL ошибка исчезает.
Шаг 2 — найти текстовые столбцы (заменить NULL на 'a' по очереди — где не ошибка, туда льёшь данные).
Шаг 3 — вытащить данные: UNION SELECT username, password FROM users в нужные столбцы.

*Почему UNION требует равное число столбцов:*
UNION склеивает две таблицы результатов строка-под-строку → колонки должны выровняться → у ТВОЕГО SELECT столько же столбцов, сколько у ОРИГИНАЛЬНОГО.
ВАЖНО: число столбцов диктует запрос ПРИЛОЖЕНИЯ (сколько разработчик вернул для показа), НЕ сколько данных нужно тебе. Код не виден → разведываем (ORDER BY / UNION SELECT NULL).
Нужных данных меньше, чем столбцов? Лишние забиваешь NULL: ' UNION SELECT username,password,NULL FROM users -- (3 столбца: 2 данных + 1 пустышка для счёта).

*Boolean-based blind SQLi:* данные не выводятся, но страница по-разному отвечает на истину/ложь (индикатор: "Welcome back" есть/нет).
Шаг 1 — подтвердить: ' AND '1'='1 (истина, индикатор есть) vs ' AND '1'='2 (ложь, нет).
Шаг 2 — посимвольно: ' AND SUBSTRING((SELECT password FROM users WHERE username='administrator'),1,1)='a → индикатор есть = символ верный. Перебор букв × позиций (SUBSTRING(pass,N,1)).
Медленно → бинарный поиск (>'m'?) + автоматизация (Burp Intruder, sqlmap).
В реальности blind чаще in-band (приложения не выводят данные/ошибки открыто).

*Бинарный поиск в blind SQLi:* вместо =' перебора по буквам — сравнение > :
' AND SUBSTRING((SELECT password...),1,1) > 'm'-- → есть индикатор = символ в верхней половине (n-z), нет = нижняя (a-m). Половинишь дальше. ~5 запросов на символ вместо ~26 (log₂26).
Строки сравниваются по алфавиту (a<b<...<z). Символ найден, когда диапазон схлопнулся до одного.

*Time-based blind SQLi* — нет видимого индикатора (ответ одинаков на истину/ложь). Индикатор создаёшь сам: ЗАДЕРЖКА ответа.
Функции: pg_sleep(10) [PostgreSQL], SLEEP(10) [MySQL], WAITFOR DELAY '0:0:10' [MS SQL].
Подтверждение: '||pg_sleep(10)-- → ответ через 10 сек = работает.
Извлечение: '||(SELECT CASE WHEN (SUBSTRING(password,1,1)='a') THEN pg_sleep(10) ELSE pg_sleep(0) END FROM users WHERE username='administrator')--
Условие истинно → задержка → верный символ. CASE WHEN = SQL-аналог if/else.
В Intruder: смотри колонку "Response received" (время мс), не Grep. Аномально долгий = верно.

*TrackingId* — cookie для отслеживания посетителя (аналитика, персонализация "Welcome back", корзина без логина). Отличие от session: session = залогиненный юзер, TrackingId = браузер/устройство независимо от логина. На реальных сайтах называется по-разному (_ga, visitor_id, _fbp), суть одна.
ГЛАВНОЕ для SQLi: неважно ЧТО за параметр и зачем — важно, что его значение попадает в SQL без параметризации. SQLi живёт в ЛЮБОЙ точке ввода: URL, форма, cookie, заголовок (User-Agent/Referer), JSON. Проверяй ВСЕ точки, не только формы.

*Time-based извлечение:* CASE WHEN (SUBSTRING(password,N,1)='X') THEN pg_sleep(3) ELSE pg_sleep(0) END. Задержка = символ верный.
Intruder Cluster bomb, как boolean, НО индикатор — колонка "Response received" (мс), не Grep. Верно = ~10000мс. Сортируй по времени.
Time-based медленный (каждый истинный ждёт задержку).

*Типы атак Burp Intruder:*
— Sniper: 1 позиция (или несколько, но по очереди, НЕ комбинируя), 1 список. Перебор одного места (пароль, символ). N payload → N запросов.
— Battering ram: неск. позиций, 1 список, одно значение во ВСЕ позиции разом.
— Pitchfork: неск. позиций, неск. списков, ПАРАЛЛЕЛЬНО (1-й с 1-м, 2-й со 2-м — «молния»). Связанные пары.
— Cluster bomb: неск. позиций, неск. списков, ВСЕ КОМБИНАЦИИ (декартово произведение). Для blind SQLi (позиция × символ). Списки 10×10 = 100 запросов.
Выбор: одно место → Sniper; все сочетания → Cluster bomb; попарно связанные → Pitchfork; одно значение везде → Battering ram.
