*CSRF (Cross-Site Request Forgery)*— атакующий заставляет браузер жертвы отправить запрос на сайт, где она залогинена, от её имени без ведома. Эксплуатирует: браузер САМ прикладывает cookie к запросу (как в XSS с HttpOnly).
Механика: evil.com с формой на bank.com/transfer + автосабмит → жертва открыла → браузер послал с её cookie банка → банк выполнил перевод.
3 условия: (1) интересное действие; (2) сессия через cookie (авто-прикладывание); (3) предсказуемые параметры + НЕТ непредсказуемого секрета.
Защита — CSRF-токен: случайный непредсказуемый секрет в запросе, атакующий не знает → не подделает. (= state в OAuth, тот же принцип.)

*CSRF vs XSS:*
XSS — атакующий выполняет СВОЙ JS НА сайте-жертве (bank.com). Код внутри доверенного сайта: читает DOM/данные, видит ответы, полный контроль. Мощнее.
CSRF — атакующий НЕ выполняет код на сайте-жертвы. Со своей страницы (evil.com) заставляет браузер ОТПРАВИТЬ запрос на bank.com с cookie жертвы. Действие выполняется, но ответ НЕ виден (Same-Origin блокирует чтение), код на сайте не бежит. Слепая отправка. Ограниченнее.
XSS обходит CSRF-защиту: JS атакующего на сайте читает CSRF-токен со страницы → подделывает запрос.
JWT и CSRF: в cookie → уязвим (авто-прикладывание); в localStorage+заголовок Authorization → НЕ уязвим (браузер не прикладывает сам). Токен в заголовке = защита от CSRF.

*Same-Origin Policy (SOP)* — правило браузера: сайт НЕ может ЧИТАТЬ данные другого сайта (origin = схема+домен+порт). JS на evil.com не прочитает с bank.com: ни ответы, ни DOM, ни localStorage, ни cookie. Стена между сайтами.
АСИММЕТРИЯ (суть CSRF): SOP запрещает ЧИТАТЬ ответ чужого origin, но НЕ запрещает ОТПРАВИТЬ запрос. Отправить на bank.com с cookie жертвы — можно; прочитать ответ — нельзя. → CSRF слепой (действие проходит, ответ не виден).
Почему localStorage-токен защищает: cookie прикладывается АВТОМАТИЧЕСКИ (уязвимо). Токен из localStorage добавляет JS ВРУЧНУЮ в заголовок — но JS атакующего (evil.com) не прочитает чужой localStorage (SOP) и не добавит токен → запрос без токена → отклонён.
*CSRF возможен:* (1) аутентификация через cookie (авто-прикладывание); (2) меняющее состояние действие; (3) нет CSRF-токена.
*НЕ возможен:* токен в заголовке (Bearer), CSRF-токен, SameSite cookie.
СМЫСЛ: эксплуатирует ложное допущение сайта «валидная cookie = осознанное действие юзера». Браузер прикладывает cookie к ЛЮБОМУ запросу, даже инициированному evil.com без ведома жертвы. Действие от имени жертвы БЕЗ кражи пароля/сессии — злоупотребление уже открытой сессией вслепую.

## Лаба: CSRF vulnerability with no defenses

### Шаги эксплуатации
1. Найти запрос, меняющий состояние (смена email): POST /my-account/change-email, параметр email.
2. Перехватить в Burp — узнать URL, метод, параметры.
3. Собрать HTML-эксплойт (форма + автосабмит) на exploit server.
4. Store → Deliver to victim → email жертвы меняется её же браузером.

### Шаблон CSRF-эксплойта
<form action="https://LAB-ID.web-security-academy.net/my-account/change-email" method="POST">
  <input type="hidden" name="email" value="attacker@evil.com">
</form>
<script>document.forms[0].submit();</script>

### Разбор
- form action = КУДА слать (полный URL эндпоинта жертвы)
- method = КАК (совпасть с оригиналом: POST/GET)
- input name = имя параметра (совпасть с тем, что ждёт сервер)
- input value = значение атакующего
- type="hidden" = скрыто от жертвы (не видит поля)
- document.forms[0].submit() = автосабмит: форма уходит САМА при открытии страницы, жертва ничего не нажимает

### Почему работает
Жертва открыла страницу → JS сабмитит форму → браузер шлёт POST на сайт-жертвы →
АВТОМАТИЧЕСКИ прикладывает session cookie жертвы → сервер видит валидную сессию →
выполняет смену email. Нет CSRF-токена = нечему остановить поддельный запрос.

### Ключевое
Путь в action, данные в input. Жертва не видит (hidden) и не нажимает (автосабмит).
Работает из-за авто-прикладывания cookie + отсутствия CSRF-токена.

*CRLF = Carriage Return (\r, код %0d) + Line Feed (\n, код %0a)*
*CRLF-инъекция:* CRLF = \r\n (%0d%0a) — разделитель строк/заголовков в HTTP. Внедряешь %0d%0a в данные, попадающие в заголовок ответа → создаёшь НОВУЮ строку/заголовок.
Механика (лаба): поиск клал ввод в Set-Cookie: LastSearchTerm=<ввод> без фильтра CRLF → внедрил %0d%0aSet-Cookie: csrfKey=... → дорисовал лишний заголовок → установил произвольную cookie.
Корень: данные пользователя в HTTP-заголовке без фильтрации управляющих символов → данные стали структурой (заголовками). Как все инъекции.
Можно: установить cookie, внедрить заголовки, HTTP Response Splitting (поддельная страница). Защита: фильтровать \r\n в вводе, идущем в заголовки.
