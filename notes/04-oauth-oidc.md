*OAuth2* — дать приложению ОГРАНИЧЕННЫЙ доступ к твоим данным в другом сервисе БЕЗ передачи пароля (делегированный доступ). Пример: сервис печати читает Google Фото, не зная твой пароль.
Роли: Resource Owner (ты) · Client (приложение) · Authorization Server (выдаёт токены) · Resource Server (хранит данные).
access token — карта-ключ: что предъявителю МОЖНО делать (права, ограничен, отзываем).

*OIDC* — надстройка над OAuth2, отвечает на «КТО вошёл». Добавляет ID token (личность: имя, email). «Войти через Google» = обычно OIDC.
Два токена: access token = права (что можно), ID token = личность (кто ты). Не путать.

Почему token > пароль: (1) least privilege — токен ограничен scope (только фото), пароль даёт всё; (2) при утечке: пароль = весь аккаунт навсегда + смена пароля запирает тебя; токен = узкий доступ, временный (протухает), отзываемый (гасишь, не трогая пароль).
*Принцип least privilege (наименьших привилегий) — дай ровно столько прав, сколько нужно для задачи*
*Принцип: не отдавай постоянный универсальный секрет там, где хватит временного ограниченного.*

*Атака 1:* подмена redirect_uri. redirect_uri — параметр в URL входа («куда вернуть токен»). Атакующий шлёт жертве ссылку на НАСТОЯЩИЙ google, но с redirect_uri=attacker.com. Жертва честно логинится → токен улетает атакующему. Опасно тем, что домен подлинный, жертва не видит подвоха → глазами не защитить, только сервер.
Корень: сервер доверяет значению из запроса, контролируемому атакующим (как alg в JWT, id в IDOR — один класс).
Fix: allowlist зарегистрированных redirect_uri, сверка EXACT MATCH (не «начинается с» — иначе photoapp.com.attacker.com обойдёт). Тот же принцип, что algorithms=["RS256"] в JWT.

*Атака 2:* нет state → login CSRF. state — случайная метка, сайт шлёт её на Google и сверяет на возврате (как номерок гардероба): «этот ответ — на мой запрос?». Без state сайт принимает чужой ответ → атакующий подсовывает свой код авторизации → жертва логинится в АККАУНТ АТАКУЮЩЕГО → её данные (фото, карта) уходят атакующему. Fix: state — случайный, привязан к сессии, проверяется. Это CSRF-токен.

access token — «на предъявителя»: даёт права, но НЕ привязан к тому, кто показывает (как наличные).
ID token — привязан через aud (для кого выписан).
*Атака 3:* сайт пускает по access token как по удостоверению → атакующий несёт чужой access token → вход под чужим именем. Fix: аутентификация ТОЛЬКО по ID token (проверять aud). access — исключительно для доступа к ресурсам.
Вместе ≠ взаимозаменяемо: оба выдаются при «Вход через Google», но ID = паспорт (кто), access = пропуск (что можно).

ID token годится для «кто вошёл», потому что (1) содержит личность и (2) привязан к получателю через aud(audience - для кого выписан). access token — ни того, ни другого: на предъявителя, без адресата.
